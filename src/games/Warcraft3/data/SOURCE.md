# Warcraft III dataset source & attribution

Two data sources:
1. **`wc3.json`** — command cards, races, grouping/conflict structure (from jcfields' editor,
   MIT) — below. Its per-command *names* are now only a fallback (see below).
2. **`wc3_names.json`** — a `code → name` map that is the **source of truth for every command
   name** the editor shows (unit-card commands, common commands, globals, and the *Miscellaneous*
   tail). Generated by `gen_wc3_names.py` from **Warcraft III's own game data** (Blizzard, copied
   out of a game install — not vendored here), where each object table (`*data.slk`) is
   paired with a set of `strings/*.txt` files that carry its display text. A hotkey triggers an
   **action**, so we prefer the button's action label (`Tip=`) over the bare object name
   (`Name=`). Resolution priority:
   - **`strings/*.txt`** (`ItemStrings.txt`, `*AbilityStrings.txt`, `*UnitStrings.txt`,
     `*UpgradeStrings.txt`, `commandStrings.txt`, `generalKeybindStrings.txt`, …) — `[CODE]`
     blocks. The **`Tip=` line = the action label** (e.g. `hbar` → "Build Barracks", `hfoo` →
     "Train Footman", `Rhss` → "Research Control Magic", `CmdMove` → "Move"). Preferred. The
     **`Name=` line** (the bare object, e.g. `hbar` → "Barracks") fills any code with no `Tip=`.
     Leveled values are stored as an unquoted comma list of per-tier labels (`Upgrade to Iron
     Forged Swords,Upgrade to Steel…`) while a name that genuinely contains a comma is quoted
     (`"Storm, Earth, And Fire"`); the generator keeps the level-1 label. Leveled tips also carry
     inline color markup + a `- [Level N]` suffix (`Holy Light - [|cffffcc00Level 1|r]`), stripped
     so a hero ability reads as just "Holy Light".
   - **`*data.slk`** (`itemdata`/`abilitydata`/`unitdata`/`upgradedata`) — the `comment(s)` column
     is an internal **dev label** (e.g. `rots` → "Rod of the Sea"). Used only to fill codes with
     no strings entry.

   `module.js` labels every command via this map, using the jcfields `wc3.json` card name only
   for the few codes the game files don't name (custom/hero placeholders like `a000`). We vendor
   only the derived flat name map, **not** the raw tables (they were removed once extracted). To
   refresh, copy the `.slk`/`*Func.txt` object tables + their `strings/` counterparts out of a
   Warcraft III install into a directory and run `python3 gen_wc3_names.py <that-dir>`.

---

`wc3.json` (unit/ability **names**, **races**, **types**, per-unit **command cards**, the
shared common-command lists, `buildCommands`, `campaignRaces`, and `shown` — the curated list of
browsable/playable unit codes) is derived from the open-source **Warcraft III Hotkey Editor** by
J.C. Fields:

- Repository: <https://github.com/jcfieldsdev/warcraft3-hotkey-editor>
- Source files: `www/scripts/data.js` (data tables) + `www/index.html` (the `#code` anchor
  links that form the `shown` allowlist — `data.units` also contains campaign/boss units that
  exist only for hotkey resolution and are not browsable — and the per-race `<h3>Melee</h3>` vs
  `<h3>Campaign</h3>` subsections, from which we derive `campaign` = the units that only appear
  in campaign, used to sort them into their own column after the melee categories)
- Author: J.C. Fields <jcfields@jcfields.dev>
- License: **MIT** (see the notice retained below)

We use it to turn the raw 4-char ability/command codes in `CustomKeys.txt` into friendly
names, to group bindings by their in-game command card, and to detect per-card hotkey
conflicts. We did **not** copy the upstream icon map (`data.icons`) or its editor code — only
the data tables listed above, re-serialised to JSON (`type` enum ints mapped to short strings;
codes matched case-insensitively, as the game itself does).

## Regenerating

`wc3.json` is static — it only changes if the upstream data does. To refresh it, fetch
`www/scripts/data.js` and `www/index.html` from the repo above and re-run the one-off converter:

```
node gen_wc3_data.js path/to/data.js path/to/index.html
```

which evaluates data.js and writes `{units, common, buildCommands, campaignRaces, shown}` with
the `type` enum mapped to strings, the `icons` table dropped, and `shown` extracted from the
index.html anchor links. (Kept out of the Python build toolchain on purpose: there is no
game-install dependency and the data rarely moves.)
